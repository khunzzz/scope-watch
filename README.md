# scope-watch

Мониторинг публичных bug bounty программ **Standoff 365** и **BI.ZONE** на Go.
Уведомляет в Telegram о новых программах, изменениях scope, выплат и правил,
закрытии и повторном открытии программ. Изменения одной компании на разных
площадках объединяются в сообщение.

## Запуск в Docker

```bash
cp .env.example .env
mkdir -p secrets data
printf '%s' 'ТОКЕН_БОТА' > secrets/tg_bot_token
sudo chown 1000:1000 data secrets/tg_bot_token
sudo chmod 400 secrets/tg_bot_token
docker compose up -d --build
```

В `.env` укажи `TG_CHAT_ID`. Чтобы узнать его, напиши боту `/start`, оставь
`TG_CHAT_ID` пустым и выполни:

```bash
docker compose run --rm scope-watch scope-watch test-notify
```

Первый успешный сбор сохраняет исходный снимок и отправляет подтверждение.
Уведомлений об отдельных программах при первом сборе нет. Далее проверка
выполняется каждые 15 минут с небольшим случайным сдвигом.

Образ содержит статический Go-бинарник и сертификаты CA, запускается с UID/GID
1000, без shell и Python. Ограничения контейнера заданы в `docker-compose.yml`.

## Локальная сборка

Нужен Go 1.27 или новее. Для обычной сборки C-компилятор не нужен.

```bash
go build -trimpath -o bin/scope-watch ./cmd/scope-watch
./bin/scope-watch --help
./bin/scope-watch run --dry-run --only standoff
```

Используем библиотеки там, где они сокращают собственный инфраструктурный код:

| Библиотека | Назначение |
| --- | --- |
| Cobra | Команды, флаги, справка, shell completion |
| godotenv | `.env`: кавычки, комментарии и приоритет окружения |
| Squirrel | SQL-запросы с параметрами; схема — `internal/storage/schema.sql` |
| modernc.org/sqlite | SQLite без CGO |
| gofrs/flock | Межпроцессная блокировка прогонов |
| go-difflib | Сравнение текстов правил |

Версии закреплены в `go.mod` и проверяются по `go.sum`.
Стандартные `net/http`, `log/slog` и `context` остаются основой сети и исполнения.

## Команды

В контейнере: `docker compose exec scope-watch scope-watch <команда>`.

| Команда | Назначение |
| --- | --- |
| `run [--dry-run] [--only standoff]` | Один сбор; `--only` можно повторять |
| `loop [--only bizone]` | Периодические сборы |
| `seed [--only standoff]` | Заменить исходный снимок без событий об изменениях |
| `status [--json]` | Программы, сбои, время успешного сбора и очередь Telegram |
| `history [-n 20] [--program tbank]` | Журнал изменений |
| `links` | Связанные программы разных площадок |
| `export [-o /data/companies.json]` | Scope компаний в JSON |
| `test-notify` | Проверка Telegram и подсказка chat_id |
| `healthcheck` | Проверка heartbeat для Docker |
| `completion bash/zsh/fish/powershell` | Скрипт автодополнения команд |

`run --dry-run` печатает сообщения, не меняет снимки/историю/очередь и не отправляет
их в Telegram. При отсутствии базы создаётся пустая SQLite-схема.
`seed` отправляет подтверждение и, как обычный прогон, досылает очередь.
Код завершения `run`: 0 — успех, 1 — ошибка площадки/доставки/хранилища,
2 — неправильные аргументы или настройки.

## Настройки

`.env` читается из текущего рабочего каталога. Уже заданные переменные окружения
имеют приоритет.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `TG_BOT_TOKEN_FILE` | — | Путь к файлу токена; приоритет над `TG_BOT_TOKEN` |
| `TG_BOT_TOKEN` | — | Токен для запуска без Docker secret |
| `TG_CHAT_ID` | — | Чат уведомлений |
| `SCOPEWATCH_DATA` | `./data` | Каталог SQLite и блокировки |
| `SCOPEWATCH_INTERVAL` | `900` | Интервал в секундах |
| `SCOPEWATCH_DELAY` | `0.4` | Минимальный промежуток между запросами площадок |
| `SCOPEWATCH_FAIL_ALERT` | `3` | Сбоев подряд до предупреждения |
| `SCOPEWATCH_HEARTBEAT` | — | Файл heartbeat фонового цикла |

## Надёжность и ограничения

- Частичные сбои сохраняют предыдущие данные программы. Ошибки списка,
  обязательного scope или подозрительное массовое исчезновение блокируют
  обновление снимка площадки.
- Удаление программы подтверждается двумя последовательными пропусками.
- Снимки, история, состояние площадок и очередь записываются одной транзакцией.
- Telegram получает сообщения из очереди по порядку. После успешного ответа
  сообщение удаляется. При неоднозначном сетевом сбое после принятия сообщения
  Telegram или остановке до удаления из очереди возможен повтор: доставка
  **at least once**, без обещания exactly once.
- Одновременно записывать данные может один Go-прогон на каталог. Блокировка
  снимается ОС при завершении процесса; оставшийся `.lock`-файл не означает зависание.
- SIGINT/SIGTERM отменяет ожидания и HTTP-запросы. Незавершённый сбор не сохраняется;
  уже зафиксированная очередь остаётся на следующий запуск.
- `status` показывает свежесть отдельно от числа ошибок. До первого успешного
  сбора явно показывает отсутствие данных.
- Scope из текста — эвристика. Текст правил сравнивается отдельно. При изменении
  версии экстрактора сравнение ассетов пропускается один раз, чтобы улучшение
  эвристики не породило ложные уведомления; текст, статусы и выплаты
  продолжают сравниваться.
- Только публичные программы. Сервис не выполняет сканирование целей.

## Архитектура

| Путь | Ответственность |
| --- | --- |
| `cmd/scope-watch` | Точка входа и обработка сигналов |
| `internal/app` | CLI, настройки, сборы, очередь и блокировка процесса |
| `internal/scope` | `models.go`, извлечение ассетов, сравнение снимков и связи программ |
| `internal/storage` | SQLite, SQL-запросы и схема |
| `internal/notify/telegram` | Формирование и доставка уведомлений |
| `internal/adapters/standoff` | DTO и сбор данных Standoff |
| `internal/adapters/bizone` | DTO и сбор данных BI.ZONE |

Начинать чтение удобно с `cmd/scope-watch/main.go`, затем `internal/app/cli.go`
и `internal/app/runner.go`. Подключение площадок находится в `internal/app/adapters.go`.
Адаптеры получают стандартный `*http.Client`; настройки транспорта и повторов
находятся в `internal/app/http.go`, разбор ответов — внутри адаптеров.
Связанные функции разделены по файлам одного пакета; отдельный пакет нужен
для самостоятельной части сервиса, а не для каждого файла.

Контракт определяется потребителем — пакетом `app`:

```go
type Adapter interface {
    Name() string
    Title() string
    Fetch(context.Context, map[string]scope.Program) (scope.Fetched, error)
}
```

Для новой площадки создай `internal/adapters/<platform>` с `adapter.go`,
`client.go`, `types.go`, `parser.go` и добавь конструктор в `newAdapters` (`internal/app/adapters.go`).
Адаптер не меняет переданный прошлый снимок, возвращает нормализованные программы,
общее количество и slug частичных сбоев. Ошибка полного списка/обязательного scope
возвращается как `error`. CLI автоматически принимает новое имя в `--only`.
Наследование, глобальная саморегистрация и контейнер внедрения зависимостей не нужны.

## Форматирование и проверки

Форматирование: `gofmt -w cmd internal e2e`. CI проверяет, что оно применено.
Длинные цепочки запросов разбиваем вручную: вызов метода на строку,
точка остаётся в конце предыдущей строки. Выполнение запроса и проверку ошибки
пишем отдельными выражениями. Крупные литералы структур — поле на строку.
`gofmt` сохраняет эти переносы и выравнивает отступы.

```bash
go mod verify
go vet ./...
go test -race -count=1 ./e2e
CGO_ENABLED=0 go build -trimpath -o bin/scope-watch ./cmd/scope-watch
```

В проекте оставлены только E2E-тесты. Для них нужен поддерживаемый C-компилятор: проверяемый бинарник собирается с `-race`.

`e2e/service_test.go` собирает настоящий бинарник и запускает его как отдельный
процесс. Локальный CONNECT-прокси и временный доверенный TLS-сертификат подставляют
ответы Standoff, BI.ZONE и Telegram. Прокси отклоняет запросы к другим адресам;
в приложение не добавлены тестовые URL или обход проверки сертификатов.

E2E проверяет исходный сбор, отсутствие повторных уведомлений, dry-run, изменения
scope, повтор запросов после HTTP 429/503, отказ и восстановление Telegram, сохранение очереди, отказ площадки,
подтверждение удаления, команды истории/экспорта, блокировку конкурирующих прогонов
и завершение по SIGTERM. Проверка сквозного сценария запускается на Unix-системах.
CI также собирает Docker-образ и запускает его CLI.

```bash
go test -v -count=1 ./e2e
```
